# 顶层架构设计：TAM-CAD

> 本文只定义架构。**不含训练、不含跑数、不含模型选型。**
> 每一节先说"这个模块要解决什么问题"，再说"它和别的模块怎么协同"，最后说"它凭什么可信"。
> 凡是实测出来的数字，都标明来源；凡是估计的，都标明是估计。

> **文档关系**：本文是**顶层架构的权威版本**。`architecture-v2-design.md`
> 是同一天早些时候的草稿，其中关于**模块 A 编码器**（图注意力、bge 文本编码器、
> 级联 Transformer）的细节仍然有效，但它的 §1.1 语料口径与 §2 的"路线是否作为条件"
> 两处已被本文实测结论取代。冲突时以本文为准。

## 0. 为什么要重做顶层架构

之前的做法是：**先有一个能跑的小模型，再往里补功能**。补的顺序是
意图识别 → 对齐 → 存储 → 信息传递。这条链路上每一环都做了，但**几何始终是
"输入参数"而不是"被建模的对象"**，于是三个问题一直悬着：

| 问题 | 现象 | 根因 |
|---|---|---|
| 定位不准 | 局部模型只能把参数指到一个 `feature` 标签上 | 设计图被压成 `context` 均值向量，几何在入口就丢了 |
| 复用时几何失真 | `target.json` 记了 `derive/state_copy`，但没人把它重放成几何状态 | 过程链里只有**数**，没有**实体** |
| 无法判合法 | 说不清"沟开在壁上还是槽底"、"两步之间特征有没有错位" | 没有实体级几何记录，也没有拓扑 |

这三件事**不是三个 bug，是一个根因**：过程链缺少一层「几何状态」抽象。
所以顶层架构必须先把这层抽象定下来，模型只是它的实现方式之一。

## 1. 实测约束（架构设计的边界条件）

全部来自 2026-11-13 的本仓库实测，脚本可复跑。

### 1.1 语料的真实规模

| 项 | 实测值 | 来源 |
|---|---|---|
| 零件（有工序链） | **6** | `设计图/geo/FAXIN/` |
| 工序图 | **75**（13/11/14/13/12/12） | 同上 |
| 名义设计图 | **19**（其中 6 个有工序链，13 个没有） | `设计图/geo/设计图/` |
| 实体总数 | **45,818** | `corpus_audit.measure()` |
| 尺寸标注 | **303** | 同上 |
| 零件级特征号总数 | 18 / 19 / 29 / 28 / 15 / 32 | `geo_state` |
| 跨工序持续存在的特征 | 13 / 15 / 23 / 6 / 11 / 26 | 同上 |

> **修正一个此前的错误口径**：曾记为"75 个零件"。实际是 **6 个零件、75 张工序图**。
> 之前几版核查脚本用**文件名**当零件键，��自己比自己，得出"75/75 稳定"的假结论。
> `corpus_audit.py` 是修正后的版本，它按**零件目录**分组。

### 1.2 语料里最要紧的三个发现

**发现 1：图纸自带零件级特征编号（这是免费的拓扑真值）**

AutoCAD 抽取的 JSON 每个实体带 `group` 字段，名字编码了三层信息：

```
serial_feature_level_label
      │      │      └── 中文特征描述
      │      └───────── 视图层级（1 = 主视图，0 = 局部/放大视图）
      └──────────────── 特征号 = **零件级**标识，同一零件的所有工序图一致
```

实测：特征号在零件内**连续**（如 C3359 的 1..32）；同一特征号在不同工序图里
指向同一个零件特征（名称可能变，`外圆` ↔ `Φ6点7外圆`）。

> **这是本项目最重要的一条实测结论**。此前的 `correspondence.py` 用"测量值+方向"
> 启发式做跨图对应，还要扣除排版偏移；特征号是**精确的**，不需要任何修正。
> 架构里跨工序的实体对应**直接用特征号**，不再依赖启发式。

**发现 2：名义设计图没有特征编号**

19 张名义设计图的 `group` 只有 `default` / `A2_PATTERN` / `ANNOTATION` 这类
图元分组，**一张都没有** `serial_feature_level_label` 形式。

> **这条约束直接决定了架构**：名义设计图与工序图**不能靠特征号对齐**。
> 名义设计图只能通过「值 + 几何」被工序图引用（这正是现有 `localization.py`
> 做的事，定位率 80.6%）。因此架构里必须区分**两类特征标识**：
> - `design_feature`：名义设计图的特征（无零件级编号，靠声明值与几何定位）
> - `part_feature`：工序图里由零件级特征号标识的特征（跨工序稳定）
> 二者的桥接就是 `localization.py` 的 `matches`。

**发现 3：工序图之间画的不是"累积状态"**

同一零件相邻两步的图纸，几何**确实在变**（`geo_state` 统计：几何改动
16/10/20/4/12/29 次，保持 19/17/39/8/14/30 次），但：
- 每张工序图只画**它自己那一步**关心的东西，不是把前面所有步骤叠起来；
- 特征号在部分步骤才出现（单工序引入 5/4/6/22/4/6 个）；
- 热处理、清洗、检测步骤**一个特征都不画**。

> **架构含义**：过程链是**状态的差分序列**，不是状态序列。每一步记录
> 「这一步把哪些特征画成什么样」，前后关系由特征号串联。
> 不能指望"重放第 3 步就得到完整的第 3 步图纸"。

## 2. 顶层架构：五层

```
┌──────────────────────────────────────────────────────────────────────┐
│ L0  语料层   图纸保真记录（entities + 特征号 + 视图 + 关系）           │
│     ← design.json v2 / geo_state.json                                 │
├──────────────────────────────────────────────────────────────────────┤
│ L1  几何状态层  ★ 这次新立的一层                                        │
│     过程链的每个节点 = 一组特征的几何状态快照 + 相对上一步的增量          │
│     state = {特征号 → (几何摘要, 声明值)}                              │
│     delta = {特征号 → (几何变化, 值变化)}                              │
├──────────────────────────────────────────────────────────────────────┤
│ L2  语义层    意图/角色/更新算子（现有能力，保留）                      │
│     roles / update / sources 指针                                     │
├──────────────────────────────────────────────────────────────────────┤
│ L3  约束层    确定性合法性内核（不可学习）                               │
│     干涉 / 错位 / 越界 / 反向 / 终检超差                                 │
├──────────────────────────────────────────────────────────────────────┤
│ L4  推理层    给定设计图 + 路线 → 生成/校验过程链                        │
│     （T1 条件式；T2 自由生成降级为对照）                                 │
└──────────────────────────────────────────────────────────────────────┘
```

**关键设计决定：L1 与 L3 不依赖任何神经网络。**

这是与"先做小模型再补功能"最根本的区别。L1/L3 是**确定性的几何计算**，
可以用规则和数值方法写死，可以用单元测试逐条验证，可以先跑通再谈模型。
如果 L1/L3 依赖模型，那么"模型输出错了几何"和"模型预测错了几何"就无法区分，
调试会陷入死结。

## 3. L0 语料层：图纸的保真记录

### 3.1 职责

把一张 AutoCAD 抽取的 JSON，变成**可逆的**几何记录。

### 3.2 结构

```jsonc
{
  "frame": { "min": [x,y], "span": [sx,sy], "unit": "mm", "scale": 4.0 },
  "views":  [ { "name": "FCFEntity1", "bbox": [...], "features": [3,9,10], "levels": [1] } ],
  "features": [
    { "id": 3, "name": "外圆", "labels": ["外圆_6直径_5粗糙度"], "levels": [1],
      "entity_ids": [...], "dimensions": [ { "index": 6, "kind": "直径" } ] }
  ],
  "entities": [
    { "id": "A1", "type": "LINE", "layer": "1", "handle": "A1",
      "groups": [ { "serial": 1, "feature": 3, "level": 1, "label": "外圆_6直径_5粗糙度" } ],
      "geometry": { "kind": "line", "start": [...], "end": [...],
                    "bbox": [...], "length": 69.0 } }
  ],
  "relations": [ { "relation": "annotation_of", "source": "D1", "target": 3 } ]
}
```

### 3.3 关键点：`frame` 让归一化可逆

现有 `design.json` 的 12 维 `numeric` 把坐标归一化后**丢弃了 `minima`/`spans`**，
所以不可逆。加上 `frame` 后：

$$x = \texttt{frame.min}[0] + \texttt{numeric}[0] \cdot \texttt{frame.span}[0]$$

`faithful.invert_numeric` 已实现并有测试（误差 < 1e-9）。
**网络输入不变**（旧 checkpoint 仍可加载），**几何判定成为可能**。

### 3.4 关系类型（7 类，对应 Graphormer 的边偏置）

| 关系 | 来源 | 置信度 |
|---|---|---|
| `same_view` | 实体同属一个 `FCFEntity<N>` 块 | 高（图纸自带） |
| `cross_view` | 实体在顶层但分属不同视图 | 高 |
| `annotation_of` | 尺寸标注 → 它所属的特征 | 高（group 字段） |
| `member_of` | 实体 → 它所属的特征 | 高（group 字段） |
| `detail_of` | 局部视图 → 它放大的主视图特征 | **中**（需规则，见 §3.5） |
| `proximity` | 同视图内几何邻近 | 计算得到 |
| `block_ref` | INSERTBLOCK → 块内实体 | 高 |

### 3.5 一个必须承认的缺口

`detail_of`（局部视图属于哪个主视图）**不能只靠几何包含关系**。实测：
把所有特征的 bbox 合并后做包含判断，2798Z 得到 91 对包含关系，但里面绝大多数是
**跨视图的重叠**（局部视图和主视图画在同一张纸上，投影上互相覆盖）。

修正：包含判断**必须在同一 level 内做**（同视图层级）。修正后
2798Z 从 91 降到 23 对，其余零件 17/94/30/17/41，总计 222 对。

> **这一条必须写进论文**：多视图图纸上，投影重叠 ≠ 拓扑包含。
> 任何"用 bbox 包含推父子"的做法都必须先做视图分离，否则学到的是排版不是拓扑。

### 3.6 L0 的四个已验证修正（2026-11-13 第二轮）

上面 §3.2–3.5 的结构在第二轮实测中暴露了四个问题。四个都已修进
`farmcad/data/faithful.py`，每个都有对应的回归测试。

**修正 1：`frame` 的作用域必须是"顶层"，不是"全图"。**

数据集的 12 维 `numeric` 是 `prepare.py` 对**图纸顶层**归一化出来的。
`frame` 若把块里的实体也算进去，最小值会偏移最多 31 mm、跨度会偏移 31 mm
（实测 2798Z-01-03、3309-07-02 两张图）。后果是**静默的**：12 维向量看上去
仍然归一化正常，但每个实体都被放在图纸上错误的位置。

现在 `extract_drawing` 写两个框：
- `frame`：**只对顶层**计算 —— 与 `prepare.py` 完全一致，实测逐项差 0.00e+00；
- `frame_all`：对全图（含块）计算 —— 这才是图纸幅面，视图几何要在它上面量。

**端到端验证**：取数据集实际发布的 `D207NQ.01` 案例，把它的 `numeric`
逐个反解回图纸坐标，与原始 JSON 的中心比对：**423 个实体，最大误差 4.83e-13，
超差 0 个**。这就是"旧 checkpoint 仍可加载"这句话的实证。

**修正 2：SPLINE 的形状在 `control_points` / `fit_points` 里，不读就没有位置。**

实测 `1340.1-02-01` 有 166 条 SPLINE、`1708C-01-02` 有 468 条 —— 占这两张图
实体的 4%。不读这两个字段，这些实体**完全没有位置**（`bbox` 为空）。
现在读，两张图的 SPLINE 无位置数从 166/468 降到 **0/0**。

**修正 3：ARC 的外接框是它扫过的扇形，不是两个端点的框；长度也是弧长不是整圆周。**

端点的框不包含弧的凸起，因此用端点算的框会把弧的实体判错位。
现在按扫过的角度重建：实测 460 条 ARC，框与真值差 0 条，长度与
`radius × sweep` 差 0 条。

**修正 4：视图不是块，视图是"图面上的若干张画"。**

这是四个修正里最重要的一个，因为它直接动摇"Topology-Aware"的立论基础。

实测：
- 块总数 1,122，其中 `FCFEntity<N>` 只有 **98** 个，装 **3,661** 个实体，
  占全语料几何的 **8%**；
- 其余 4,231 个块内实体，与顶层实体**几何重合的只有 1 个**（0.0%）——
  所以块不是顶层的拷贝，块也不是"视图的另一种叫法"；
- 顶层实体与块内实体**没有一个**在几何上重合（0.0%），所以顶层也不是展开后的块。

结论：**块只是命名上的容器，视图必须从几何里恢复。**
按图面空间聚类恢复后：2798Z-01-03 得到 **10 张画**，其中 9 张有实质内容
（分别 369 / 349 / 299 / 173 / 129 / 104 / 65 / 61 / 48 个实体），
装下 1,597 / 1,600 个有形状的实体，**没有单元素画**。
而按块划分只有 8 个"视图"，其中 `_TOP` 一家占 1,919 个实体（90%）。
一个把 90% 几何塞进一个桶的划分，**没有分开视图，只分开了块**。

最大的那张画（P01，369 个实体）的外接框覆盖整张图面，它是图框和图面装饰，
不是零件的一个视图；**这一点要如实说明**，不能把它算成一个视图。

现在 `extract_drawing` 同时输出两套：
- `views`：按块（图纸自带，命名依据）
- `pictures`：按图面空间聚类（几何恢复，是真正的视图）

标注（尺寸/文字）**不参与空间聚类**，而是事后归到最近的一张画——
因为尺寸的文字写在离被测形状很远的地方，把它按位置聚类会把不相干的画拉到一起。
（这一点不是理论顾虑：不这样做时聚类数从 10 涨到 36，产生了大量单元素假画。）

## 4. L1 几何状态层 ★ 核心新增

### 4.1 状态是什么

**过程链的一个节点 = 一步工序之后，零件几何状态的快照。**

但快照不是"整张图"，而是「**这一步所涉及的特征的几何状态**」：

$$\text{State}_t = \left\{ f \mapsto \left( \mathcal{G}(f,t),\; v(f,t) \right) \right\}$$

- $\mathcal{G}(f,t)$：特征 $f$ 在步骤 $t$ 被画成什么样（几何摘要）
- $v(f,t)$：特征 $f$ 在步骤 $t$ 声明的值（mm）

**只存被画出来的特征。** 热处理步骤的特征集合为空——这是对的，
因为热处理不改几何，它的"状态"等于上一步，不需要单独存。

### 4.2 增��：级联的载体

$$\Delta_{t} = \text{State}_t \ominus \text{State}_{t-1}$$

级联不是"每步独立查设计图"，而是**沿链累加增量**：

$$\text{State}_t = \text{State}_0 + \sum_{\tau \le t} \Delta_\tau$$

`Δ` 有三类：
- `value_delta`：值变了（外径 65.9 → 64.2）
- `geometry_delta`：几何变了（半径跨度、长度跨度、实体数、bbox）
- `introduced`：特征第一次出现（这一步新开的槽）

### 4.3 为什么用「特征号」而不是「实体 handle」做状态键

实测：同一特征号在不同工序图里的 **handle 集合不同**（91/94 个特征号如此，
因为每次导出都会重排 handle）。

> 所以状态键必须是**特征号**，handle 只能作为**单张图内部**的实体标识。
> 这一条如果搞错，跨工序的级联会全盘失效——而且不会报错，只会静默地学错。

### 4.4 实测产出

`chainmodel/data/geo/*.json`，6 个零件：

| 零件 | 工序 | 特征 | 跨工序特征 | 单工序引入 | 值改动 | 几何改动 | 矛盾 |
|---|---|---|---|---|---|---|---|
| 2798Z-01-03 | 13 | 18 | 13 | 5 | 3 | 16 | 0 |
| 3309-02-02 | 11 | 19 | 15 | 4 | 0 | 10 | 0 |
| 3309-07-02 | 14 | 29 | 23 | 6 | 1 | 20 | 0 |
| 3309-09-01 | 13 | 28 | 6 | 22 | 0 | 4 | 0 |
| 4362.52-01-03 | 12 | 15 | 11 | 4 | 1 | 12 | 0 |
| C3359-08-01 | 12 | 32 | 26 | 6 | 3 | 29 | 0 |

矛盾（方向反转、特征号复用）全部为 0 —— **语料本身自洽**，可以当 ground truth。

## 5. L2 语义层：保留现有能力

现有的 `LocalPredictor` 做的是：给定（工序, 参数, 已发出记录），
预测这个参数指向哪个特征、什么角色、怎么更新、数值多少。

**这一层不重写**，但输入要改：

| 现在 | 改成 | 理由 |
|---|---|---|
| `design.context`（均值向量） | `design.tokens`（实体+特征+要求的 token 池） | 均值是信息瓶颈 |
| 12 维 `numeric` | + 保真 `geometry` + `frame` | 可逆 |
| 无拓扑 | + 7 类关系边 | 拓扑是论文卖点 |
| 无状态 | + `State_{t-1}` | 级联的前提 |

## 6. L3 约束层：确定性合法性内核

**不可学习。** 输入几何状态序列，输出"这条链合不合法"。

### 6.1 五个检查器

| 检查器 | 判据 | 数据依赖 | 当前状态 |
|---|---|---|---|
| `no_interference` | 同视图内两实体重叠占短者 ≥ 50% | 实体几何 | ✅ `topology.find_interferences` |
| `no_self_intersection` | 轮廓闭合且不自交 | 实体几何 | ✅ `topology.check_loop_legality` |
| `no_displacement` | 跨步对应后残余位移 > 阈值 | 跨步对应 | ✅ `correspondence`（需换成特征号对应） |
| `monotone_progress` | 去料工序的值单调变小 | 状态序列 | ✅ `geo_state.check_chain` |
| `final_meets_design` | 终检值落在设计区间 | 状态 + 要求 | ⚠️ 需要设计图桥接 |

### 6.2 三个判据的分工（这是论文的一个论点）

- **干涉**（interference）：两个实体在**同一视图**里占同一块地方 → 约束冲突
- **错位**（displacement）：同一个特征在相邻两步之间**位置变了** → 级联没对齐
- **合法性**（legality）：轮廓自交、方向反转 → 实体描述的实体不存在

> 三者**不可互相替代**。论文需要给出的是"这三个判据各自能抓到什么错"，
> 而不是笼统的"我们能判合法性"。注入错误实验（§8）就是分别针对三者的。

### 6.3 干预的方向

`no_interference` 已有实测：原始 1753 处 → 剔除代理实体 `HIDE_*`、
同几何画两遍、端点相接余量后 → 约 920 处 "部分重合" → 再按覆盖度分类 →
只剩"覆盖 <50% 且重叠 <1mm"的才是真干涉。

> **这个过程必须在论文里如实写**，不能只报最终数字。

## 7. L4 推理层：任务定义

### 7.1 T1（主线）：条件式

**输入**：设计图 D（保真几何）+ 路线 O（工序序列 + 每步的 feature_keys）
**输出**：每一步的
1. 绑定：参数 → 设计特征 / 要求 / 来源状态
2. 几何操作：这一步对每个特征做什么（改值 / 改几何 / 引入）
3. 增量 Δ（供级联累加）

**为什么路线是条件不是目标**：
- `route_templates_v1.json` 已给出 `stage_order` 与 `feature_keys`
- 本机 8 GB 装不下 Qwen3.6-27B（51.75 GiB）
- 25 个带标签案例不足以训自回归解码器

### 7.2 T2（对照）：自由生成整条路线

降级为 GRU 对照基线。**不投入深度模型。**

### 7.3 T3（新增，本文真正的贡献）：修改合法性

**输入**：设计图 + 路线 + **一次设计变更**（如加一道凹槽）
**输出**：级联重放后的状态序列 + 合法性报告

这是论文标题 *Cascaded Modification* 的落点，也是目前完全空缺的一环。

### 9.1 协同关系（谁调用谁）

```
M0 ──► M1 ──► M2 ──┬──► M5（合法性内核，确定性）
                    ├──► M4（几何操作头）
                    └──► M6（级联推理）
M0 ──► M7（编码器）──► M3（语义绑定）
                              └──► M6
```

### 9.2 三条硬边界（防止又变成"什么都搅在一起"）

1. **M5 不依赖 M7。** 合法性判定是纯几何计算。如果它需要模型输出，

2. **M2 不依赖 M7。** 几何状态是图纸的直接读出，不是预测。
3. **M3 是唯一有"旧能力"包袱的模块**，且它的验收线是
   **不低于现有 50 万参数的 `LocalPredictor`**（gold 指标）。打不过就回退。
