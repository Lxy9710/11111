## 3. ⚠️ 但 1.0 不可信：发现了**目标级划分泄漏**

### 3.1 现象

按**完整目标内容**（工序序列 + 参数序列 + 每条 event 的全部标签与数值）做指纹：

```
DISTINCT FULL TARGETS: 24
（25 个案例中只有 2 个共享目标）
```

看起来没问题。但按**粗粒度监督模式**（工序 + 参数 + features/requirements 绑定 + update，
**忽略具体数值**）做指纹：

```
DISTINCT COARSE SUPERVISION PATTERNS: 7
  4d50f2b36ada  n=19  {'train': 14, 'test': 2, 'validation': 3}
  095accbfc6a5  n=1   {'train': 1}   6006FBC1/P4YA6.66
  e9ae8bfb6a44  n=1   {'train': 1}   C180506K1NW1R3U(H).56
  e6c995bfd77f  n=1   {'train': 1}   C206NW1U(H).56
  e5ed8b2ddfce  n=1   {'train': 1}   C306NW1U(H).56
  e9f2d482f7fd  n=1   {'train': 1}   D207NQ.01
  b26910de9466  n=1   {'train': 1}   C205NW1U(H).56
```

**19 个案例（14 train / 3 validation / 2 test）共享同一个粗粒度监督模式。**
由于 `build_cage_case.py` 用**固定类别路线模板**生成保持架目标，
所有保持架案例的工序序列与参数绑定完全相同——**只有数值不同**。

现有划分检查（`assign_splits.py`）只禁止：
- 同族跨 split；
- **设计指纹**（`object_hash` 设计去掉 `case_id`）跨 split。

**没有任何检查禁止「同一监督模式」跨 split**。设计指纹确实不同（不同图纸），
所以检查通过——但**监督信号实质相同**。

### 3.2 决定性实验：模型在读设计图吗？

把 **test 的目标**配上一个**完全错误的 train 设计**（不同图纸、不同特征）：

| 配对 | features | requirements |
|---|---:|---:|
| `C1000909NW1U(H).66` + 自己的设计 | 9/9 | 6/6 |
| `C1000909NW1U(H).66` + `3C204X1W1.56` 的设计 | **9/9** | **6/6** |
| `C1000909NW1U(H).66` + `3D207NW1Y.56` 的设计 | **9/9** | **6/6** |
| `C840207NW1U(H).56` + `3C204X1W1.56` 的设计 | **9/9** | **6/6** |
| `C840207NW1U(H).56` + `3D207NW1Y.56` 的设计 | **9/9** | **6/6** |

**换成别的图纸，指标一点不掉。**

对照实验：把设计里的**特征 id 打乱**（几何内容不变，只改标识）：

| case | features | requirements |
|---|---:|---:|
| `C1000909NW1U(H).66` | 2/9 | 4/6 |
| `C840207NW1U(H).56` | 0/9 | 1/6 |

**结论**：

- 模型确实在用 `feature_id` 这个**符号标识**（打乱就崩）；
- 但它**不关心该特征对应的几何内容**——换成别的图纸的同名特征，照样全对。

也就是说：模型学到的是
**「按模板顺序把参数绑到按位置排好的特征槽位」**，
而不是
**「按几何语义把参数绑到正确的特征」**。

这与 §3.1 的诊断完全吻合：19 个案例的监督模式相同，
模型只需要记住一条固定绑定表即可满分。

### 3.3 这意味着什么

| 之前可能的表述 | 实际成立的表述 |
|---|---|
| "模型能从设计图恢复参数的对象归属" | ❌ 不成立。换图仍满分。 |
| "特征/要求指针准确率 1.0" | ⚠️ 只在「模板监督模式唯一」的退化设定下成立。 |
| "参数头突破了架构天花板" | ✅ **成立**。0.222 → 1.0 是真实改进（同一 checkpoint 对比）。 |

`parameter` 头的改进是**真实的**——因为它在**同一案例内**区分不同参数实例，
这需要知道本工序已发出哪些参数，与跨案例泄漏无关。
但 `features` / `requirements` / `update` 的 1.0 **不可作为论文结论**。

## 4. 需要补的检查与数据工作

### 4.1 划分检查：增加「监督模式」维度

`assign_splits.py` 应在族与设计指纹之外，追加：
**粗粒度监督模式（工序+参数+绑定）不得跨 split**。

按当前数据，这条检查会直接判定现有划分**不合法**，必须重划。

### 4.2 数据侧的根本问题

保持架用**固定类别路线模板**生成目标 → 监督模式高度同质。
要产生有区分度的评测，需要：

1. **路线条件化**（R1/R2/R3）：让目标随设计证据变化；
2. **不同族走不同路线变体**（`6006FBC1` 的 24 道 vs `D106NW1` 的 28 道）；
3. **绑定依几何而变**（如 `pocket_radius` vs `pocket_diameter`、
   圆孔 vs 椭圆孔导致的不同参数集合）。

第 3 点尤其关键：目前 `pocket_radius` / `pocket_diameter` 的差异**只体现在数值**，
不体现在**参数集合**上，所以模型无从学习"几何→参数集合"的映射。

### 4.3 评估协议应加入的设计扰动测试

把「设计打乱/换图」做成**常驻指标**（design-ablation）：
报告"输入设计被破坏时指标下降多少"。
若指标不降，说明模型没在用设计——这比任何单一准确率都更能暴露退化。

| R1/R2/R3 路线条件化 | ⏳ 未实施（现在**更该做**了，它正是解 4.2 的手段） |
| 设计扰动指标 | ⏳ 未实施 |

**结论**：现在**不能**把 `v3` 的 1.0 写进论文。
但这轮工作不是白做——它暴露了数据集最核心的问题：
**同质模板 + 弱监督 = 无法评测泛化**。这正是 §3.8「数据构造」在方法论上
必须处理的问题，而 R1/R2/R3 路线条件化就是解法。
